# Space research pipeline v1

`space-research.v1` expands the public `learning.space.research.v1` corpus. It reads one or two published subject IDs from Tower, proposes at most three one-hop supporting concepts and three NASA/ESA primary pages, retrieves those pages, checks exact excerpts and section locators for every proposed concept and relation, and stages an idempotent candidate. The final step reports `awaiting_independent_curator_review`; there is no review or publish step. The five private learning pipelines and Piper route are separate.

The candidate key is stable for corpus, published graph version, selected subjects and source URLs. A repeated run reuses a staged candidate only when its addition matches apart from retrieval/review dates; changed claims under the same key fail clearly. Tower receives `{id, baseVersion, addition}` through a broker-signed NIP-98 call. Candidate status can be inspected with `bun clis/space-research.ts status <candidate-id>`, and pipeline status with `bun clis/pipelines.ts show <run-id> --bot-crypto`. The signed CLI requires an agent session with `SESSION_ID`, `WINGMAN_CAPABILITY`, `WINGMAN_URL` and configured `PIPELINE_TOWER_URL`. It has no raw-key or learner identity option. Tower must allowlist the staging bot in `LEARNING_CURATOR_NPUBS`; if that mapping is missing, staging fails with `curator_forbidden`. Add the bot as an explicit curator rather than asking Pete to sign routine staging actions. Independent review uses a different allowlisted curator signer.

The source-only test uses a fake primary page and disposable candidate API. It does not call the live Tower. Locators and exact excerpts must both appear in retrieved page text. Tower's `reviewedAt` source field currently receives the automated citation-check date in staged additions; independent curator review is recorded separately on the candidate before publication. The Tower staging and review endpoints perform final merged-graph checks, including global prerequisite cycles, and reject invalid additions before candidate persistence. The pipeline also checks cycles in its bounded published walk.

## Activation after runtime update

The committed definition is copied into the shared pipeline directory by the loader on startup. The scheduler now supports `enabled: false` at creation and does not attach a cron watcher for a disabled job. The running Autopilot has not been restarted, so do not create a schedule against the old runtime. After an operator activates the new runtime and verifies the definition appears, Rick can create a disabled weekly template from an authorized brokered session:

```sh
bun clis/scheduler.ts create --name 'Space public research review' --action-type pipeline --pipeline-definition-id space-research.v1 --pipeline-input '{"subjectIds":["moon-phases-research"]}' --cron '0 9 * * 1' --timezone Australia/Perth --enabled false --bot-crypto --json
```

Inspect the returned job and confirm `enabled: false`. A disabled job cannot be manually triggered through the scheduler. From an authorized brokered session, trigger a deterministic source-only run with `bun clis/space-research.ts run --ids moon-phases-research`; this posts to `/api/pipelines/definitions/space-research.v1/runs?async=1`. Inspect its run ID with `bun clis/pipelines.ts show <run-id> --bot-crypto` and its steps with `bun clis/pipelines.ts steps <run-id> --bot-crypto`; inspect the staged candidate with `bun clis/space-research.ts status <candidate-id>`. `bun clis/scheduler.ts list --bot-crypto --json` and `bun clis/scheduler.ts runs <job-id> --bot-crypto --json` inspect schedule history. Once Tower is live, curator delegation is configured and the manual run stages a candidate successfully, the operator can enable the job with `bun clis/scheduler.ts update <job-id> --enabled true --bot-crypto`. Scheduled runs never publish. Review and publication remain explicit Tower curator actions.
