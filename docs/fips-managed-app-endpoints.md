# FIPS managed-app endpoints (PoC)

Autopilot can bundle and boot a FIPS v0.5.0 node, then expose every running
managed web app at a stable mesh-only URL without DNS registration:

```text
http://<autopilot-fips-npub>.fips:<webAppPort>/
```

The listener binds only the node's exact `fips0` IPv6 address and transparently
forwards TCP to `127.0.0.1:<webAppPort>`. It does not rewrite paths, hosts,
redirects, cookies, SSE, WebSockets, uploads, or streamed responses. FIPS is a
private transport; each WApp must still authenticate and authorize its users.

Native macOS/Bun deployments are supported as well; see
[`fips-native-macos.md`](./fips-native-macos.md). They use the upstream system
LaunchDaemon and `/var/run/fips/control.sock`, not the Docker control socket.

## Enable in Docker

Provision the normal Docker instance first, then include the opt-in overlay:

```bash
bun run docker:provision --admin-npub npub1...
docker compose -f docker-compose.yml -f docker-compose.fips.yml up -d --build
```

The overlay is deliberately separate because FIPS needs privileges ordinary
Autopilot installs do not need:

- `/dev/net/tun`
- `NET_ADMIN`
- IPv6 enabled in the container network namespace
- the existing persistent `/app/data` volume

At container boot, the root entrypoint starts FIPS and applies its nftables
policy, then launches Autopilot as the unprivileged `wingman` user. The FIPS
identity is generated by the daemon at `/app/data/fips/fips.key`, remains mode
`0600`, and is never passed through argv, environment variables, logs, or app
API responses. The public identity is `/app/data/fips/fips.pub`.

The generated config enables:

- a persistent node identity;
- `fips0` TUN networking;
- open Nostr rendezvous and endpoint advertising, so a WMapp with the node npub
  can discover it without a preconfigured IP address;
- the shared `wingman-fips-poc-v1` rendezvous namespace used by WMapp (FIPS
  rejects advertisements from a different application namespace);
- UDP NAT traversal;
- no server-side `.fips` DNS listener, because WMapp supplies client DNS.

To supply a custom persistent config, mount or create it at
`FIPS_CONFIG_PATH` before boot. Keep `node.identity.persistent: true`, the
configured control socket aligned with `FIPS_CONTROL_SOCKET`, and Nostr
rendezvous enabled. Set `node.rendezvous.nostr.app` to exactly
`wingman-fips-poc-v1`; startup fails with a remediation message rather than
silently advertising into a namespace WMapp will reject. Static peers can
replace Nostr as a transport bootstrap only after this PoC's discovery
contract is changed on both sides.

## Firewall posture

The entrypoint applies upstream's `fips0`-only default-deny nftables baseline.
It allows established/related traffic, ICMPv6 echo requests, and TCP ports
`41000-65535`, the managed web-app allocation range. Traffic on non-FIPS
interfaces returns from this table immediately.

This range rule is a PoC limitation: it is narrower than exposing all `fips0`
listeners but is not an exact dynamic set of currently assigned ports. WApps
remain responsible for service authorization. A production version should
maintain an nftables set containing only live assigned app ports.

The container supervises FIPS and Autopilot as one unit: if either process
exits, the other is stopped and Compose's existing `unless-stopped` policy
restarts both while preserving the FIPS identity. The PoC reports listener
setup failures, but it does not continuously probe individual listeners or
interface health between process exits. WMapp should therefore still treat a
connection failure as authoritative even if the last reported descriptor is
`listening`.

## Endpoint API and CLI

Authenticated app reads include a public descriptor at `app.fips` and at
`app.status.fips`:

```json
{
  "enabled": true,
  "nodeNpub": "npub1...",
  "meshAddress": "fd00::...",
  "port": 41024,
  "url": "http://npub1....fips:41024/",
  "status": "listening"
}
```

Possible states are `disabled`, `unavailable`, `listening`, `conflict`, and
`error`. A FIPS failure does not stop the underlying app. The implementation
fails closed: it never substitutes a public URL and labels it as FIPS.

JSON CLI output includes the same descriptor. Text output from
`bun clis/appctl.ts list` includes the FIPS URL and state when available.

For deterministic tests outside the bundled container, both public overrides
may be supplied together:

```env
FIPS_APPS_ENABLED=true
FIPS_NODE_NPUB=npub1...
FIPS_MESH_ADDRESS=fd00::...
```

Never put a FIPS nsec in configuration overrides or ordinary environment
variables.

## End-to-end check with WMapp

1. Start Autopilot through the FIPS compose overlay.
2. Start a registered `webApp: true` app and inspect `app.fips.url`.
3. Pair or discover the Autopilot node from WMapp's bundled FIPS node.
4. Open the FIPS URL in WMapp's embedded browser.
5. Confirm the page, static assets, redirects, and WebSocket/SSE features load.
6. Use the existing `window.nostr` bridge to log in.
7. Stop WMapp's FIPS node and confirm the URL becomes unreachable.

Do not restart a live Autopilot solely to validate this PoC without operator
approval. Existing processes need a normal approved restart before the new
entrypoint, daemon, and ingress manager take effect.
